IVModule Specifications

Each module below states its purpose, its interface, its implementation notes, and — most importantly — its failure modes. A specification that lists only what a module does is half a specification; the failure modes are what determine whether the research survives contact with real data.

4.1 Ingestion layer (L1)

4.1.1 Shared HTTP client

Every network call in the system goes through one client. This is not over-engineering — rate limiting and retry are the difference between a pipeline that completes and one that dies on a 429 in week two.

class HttpClient:
    def get(self, url, params=None, headers=None) -> Response
    def get_json(self, url, params=None) -> dict
    def get_with_backoff(self, url, *, max_attempts=5, backoff="exponential",
                         base_delay=1.0, respect_retry_after=True) -> Response
  • Backoff: exponential with jitter, capped at 60 s. Honours Retry-After when present — several free endpoints send it and ignoring it gets the IP throttled.
  • Per-host rate limiting: a token bucket per host, configured in config/sources.yaml. Default 1 request/second, 10 requests/minute for FRED, 20/minute for CoinGecko free tier.
  • Circuit breaker: after 5 consecutive failures against a host, open the circuit for 15 minutes and mark the source degraded. Prevents one dead endpoint from consuming the entire run's time budget.
  • Timeout: connect 10 s, read 45 s. A hung request must not hold a slot in the rate limiter.

4.1.2 Exchange price collector

GET https://api.binance.com/api/v3/klines
    ?symbol=BTCUSDT&interval=1d&startTime=...&limit=1000
  • Pagination: paginate backwards from the present until the requested start date, one 1000-row page at a time. 2020-01-01 → 2026 is ~2,400 days, so ~3 pages per asset. Trivial, but must be implemented.
  • Symbol mapping: the config uses BTC/USDT; Binance wants BTCUSDT. Map centrally, never ad hoc.
  • Invalid-symbol handling: Binance returns HTTP 400 with "Invalid symbol" for unknown pairs. Catch this specifically, mark the symbol as unavailable, and continue. Do not treat it as a transient error — retrying a delisted pair 5 times wastes a minute per asset.
  • Market-cap ranking is a separate call from /api/v3/ticker/24hr or CoinGecko. Binance volume ≠ market cap, so tier assignment must use CoinGecko for market cap and Binance for volume.

Failure mode: the delisted-asset trap

T3 assets are, by definition, new and short-lived. Some will be delisted during the project. A collector that treats a delisting as a fatal error will fail the whole run for one dead coin. A collector that silently skips it will produce a panel with a gap that looks like a data outage rather than a delisting. Record delistings explicitly with a status field and surface them in the dashboard's data-quality panel. A delisted asset is a legitimate observation about the risk profile of T3 assets and is worth reporting.

4.1.3 News RSS collector

  • Parsing: feedparser handles RSS and Atom. Each feed yields entries with title, summary/content, published date, link, source.
  • Full text: RSS summary is often a truncated first paragraph. Full article text requires fetching and parsing the article page, which is slow and fragile. Decision: use headline + summary for the primary corpus, and document it as a limitation. Kreuzer et al. (2026) used full article bodies and noted that headline-only approaches are used elsewhere in the literature — so this is a defensible, citable design choice, provided it is stated.
  • Timezone normalisation: RSS timestamps arrive in mixed timezones and formats. Parse to UTC, then truncate to the UTC calendar date. A news item published at 23:50 UTC belongs to that UTC date, and the date boundary convention must be stated in the thesis.
  • Asset attribution: an article is assigned to an asset if the asset's symbol or name appears in the headline/summary. Use word-boundary matching on a curated alias list (BTC, Bitcoin, XBT). Handle the alias case explicitly: "ETH" is a common substring — match on word boundaries, never substring containment, or "ETH" matches "whether" and every article about anything becomes ETH news.
  • De-duplication: the same story is syndicated across feeds. De-duplicate on a normalised title hash (lowercase, strip punctuation and stopwords) before scoring, or one event will be counted several times and inflate the daily article count.

4.1.4 Macro collector and the release-date problem

FRED series have release dates that differ from observation dates. A CPI print for March 2024 is released in mid-April. Using the observation date in a feature creates a look-ahead bias of weeks — the model would "know" the CPI value before it was published, which is the kind of error that produces spectacular backtest results and a failed defence.

The rule

Every macro series is stored with both observation_date and release_date, and the alignment engine joins on release_date. If a release date is unavailable for a series, use the standard convention of a documented lag offset (e.g. CPI released ~2 weeks after month end, unemployment ~1 week after) and state the offset in the data dictionary. This single decision protects the integrity of every macro feature in the project.

4.1.5 Orchestration

The daily job runs a fixed stage graph: price → macro → news → sentiment_proxy → onchain → features → registry. Each stage declares its inputs and outputs so the orchestrator can run only the stale stages — if price data is fresh but news is not, only news is re-collected. The run writes a manifest and exits non-zero if a source is degraded for more than three consecutive days, which is the trigger for the risk mitigation in Part VIII.

4.2 Sentiment engine (L2)

This is the module that determines whether the project answers RQ1, so it is specified in full detail and must be implemented exactly as described — it is the direct reimplementation and extension of Kreuzer et al. (2026), and any deviation must be documented as a deviation.

4.2.1 Stage 1 — Tokenisation and cleaning

  • Lowercase; strip URLs, HTML entities and markdown; collapse whitespace.
  • Tokenise; remove a standard English stopword list.
  • Lemmatise to match Kreuzer et al. (2011-based) methodology. Use NLTK's WordNet lemmatiser.
  • Keep the token stream available for density computation — the crypto-density weight is computed on the pre-stopword token list, since crypto terms are content words and would survive stopword removal anyway. State the convention explicitly.

4.2.2 Stage 2 — Baseline financial sentiment (the comparison arm)

Implement the Loughran–McDonald (2011) financial sentiment dictionary: positive, negative and negated word lists. Score as in Kreuzer et al. (2026):

Sent_i = (#positive words − #negative words) / #all words        →  [−1, +1]

The dictionary is freely available from the McDonald lab (Loughran-McDonald Financial Sentiment Dictionary, LoughranMcDonald_SentimentWordLists_2018.xlsx). Download it once, vendor it into data/reference/, and record the version and checksum in the data card. Do not rely on a live download at runtime.

This is the baseline arm for RQ1 and must be implemented independently of the crypto arm, not derived from it.

4.2.3 Stage 3 — The crypto lexicon

Build a crypto-specific dictionary of approximately 150 terms, following Kreuzer et al. (2026). Sources to combine:

  • Glossaries from established crypto reference sites (terms, categories, and — critically — which are sentiment-bearing and which are neutral topic words).
  • The Bitcoin whitepaper (Nakamoto, 2008) for technical terminology.
  • Crypto-relevant academic literature, including the four papers in this repository.
  • Terms harvested from the project's own news corpus: tokens that appear disproportionately in crypto news relative to general financial news are crypto-specific by construction.

Critical distinction the lexicon must respect

In Kreuzer et al. (2026) the crypto dictionary serves a different purpose from the financial dictionary, and conflating the two will break the method. Words like blockchain, bitcoin, altcoin, whale, rug pull are topic markers, not sentiment terms — they carry no positive or negative polarity in themselves. They are used to compute the crypto density, which then weights the sentiment score. Words like crash, surge, scam, hack, ban are sentiment-bearing and may appear in the crypto dictionary, but they also often appear in the financial dictionary, which is where the polarity is applied.

Implementation: maintain two lists — CRYPTO_TOPIC_TERMS (for density) and CRYPTO_SENTIMENT_TERMS (crypto-specific polarity that the financial dictionary misses, e.g. rug pull, rekt, moon, FUD). Each term must be assigned to exactly one list, and the assignment must be reviewed by at least two team members and recorded in the lexicon file with a comment justifying the polarity choice. This lexicon is a genuine research artefact — it goes in the appendix with its construction protocol (Appendix D).

4.2.4 Stage 4 — Crypto density weight

CDW_i = n_crypto(i) / n_total(i)        # crypto-specific terms / total terms in article i

Note on the denominator: Kreuzer et al. define density over sentences in one formulation and over terms in another. Implement over terms (sentence counts require a parser and add noise), and document the departure. The property that matters — density measures how crypto-relevant an article is — is preserved.

4.2.5 Stage 5 — Crypto-weighted sentiment

SentCrypto_i = CDW_i × Sent_i

Then aggregate to a daily per-asset score by arithmetic mean over that asset's articles for the day:

SentCrypto_{asset,day} = (1/N) × Σ_{i=1..N} ( CDW_i × Sent_i )

4.2.6 Stage 6 — Aggregation and derived sentiment features

  • Daily mean over the asset's articles (matching Kreuzer et al.).
  • Also compute: mean positive fraction, mean neutral fraction, mean negative fraction, mean CDW, article count, source count.
  • Derived: EWMA with 3-day half-life, rolling z-score over 60 days, 1-day and 5-day momentum.
  • Carry-forward rule: on a day with zero articles for an asset, carry the previous day's value forward but set a binary sent_stale flag. Do not silently interpolate. Kreuzer et al. note that ~90% of classified articles are negative, so missingness is not random and treating it as random would bias the series.
  • Negative-sample bias: with a ~90% negative article base rate, the daily mean sentiment is structurally negative and its absolute level is not very informative. The changes and the z-scores are the informative parts. This is exactly why RQ2 should be formulated in terms of elasticity and interaction coefficients rather than raw levels — and it is worth stating explicitly in the thesis, because it shows you understood the measurement rather than just running the pipeline.

4.2.7 Stage 7 — Validation of the sentiment layer

Before any model is trained, the sentiment module must pass these checks:

CheckRequirement
Manual labelling agreementTwo team members independently label a random sample of 200 articles positive / neutral / negative. Report Cohen's κ. Expect κ ≥ 0.6; below 0.4, the lexicon needs work before proceeding.
Known-polarity validationScore a benchmark set of finance-domain sentences with known polarity (e.g. the Financial PhraseBank). Report accuracy and F1. A crypto dictionary should not degrade performance on general financial text by more than a few points.
Face-validity spot checkManually inspect the 10 most positive and 10 most negative scored articles. If the rankings look wrong, the pipeline is broken regardless of what the metrics say.
Source-bias checkCompare sentiment distributions across feeds. A single feed dominating the corpus will make the "sentiment" measure a proxy for that feed's editorial policy.
Leakage auditAssert that no sentiment feature for day t derives from an article published after the end of day t. Automated test, not manual.

Table 4.1 — Sentiment module acceptance criteria. These are gates, not nice-to-haves: the model results are uninterpretable if the sentiment measure is unreliable.

4.3.2 Macro and cross-market features

Macro series (from FRED, with release-date alignment): Fed funds rate, CPI, unemployment rate, real yield (TIPS 10y), broad dollar index, gold price, VIX, S&P 500, NASDAQ. Derived macro features:

  • Surprise variables: following Kreuzer et al. (2026), compute actual minus consensus. Consensus from FRED requires an extra series; where unavailable, use the change from the previous release as a proxy and label it as such — do not call a first-difference a surprise.
  • Lagged macro: real yield at lags 1/3/5/10 (monetary policy transmits with a delay — the transmission lag is the point of including it).
  • Standardised risk: VIX z-score, credit-spread proxy, yield spread (10y − 2y).
  • Liquidity: Fed balance sheet − TGA − RRP, weekly change (as in Wang 2026).
  • Equity linkage: DJIA/NASDAQ daily returns, gold returns, DXY returns — all lagged by one day to avoid same-day simultaneity assumptions.

4.3.3 Cross-asset contagion features — the core new module

This module implements contribution C2 and is the part of the system with no precedent in the four reference papers. It has three stages.

Stage 1 — Lead–lag estimation

For each ordered pair (i, j) of assets, and for each lag ℓ ∈ {0, 1, 2, 3, 5, 7, 10}, estimate the cross-correlation between sentiment of i at time t and the forward return of j at t:

ρ_{i→j}(ℓ) = corr( SentCrypto_{i,t},  y_ret_{j,t+ℓ} )

Estimate this on the training window only, then freeze the estimated lag structure for the test window. Estimating lead–lag on the full dataset and then using the resulting features in a test-set evaluation is leakage of the most consequential kind — it lets the model know in advance which cross-asset pair is predictive.

Use a Newey–West adjusted test statistic on the correlation for significance, since daily financial series are serially correlated and a naive t-test will over-reject. Kreuzer et al. (2026) use exactly this correction for the same reason.

Stage 2 — Contagion feature construction

For each asset j and each lag ℓ selected in stage 1, construct the feature:

xasset_{j,t}^{i,ℓ} = SentCrypto_{i, t−ℓ}         for each significant source i

Restrict to sources whose ρ is significant at α = 0.05 on the training window, and cap the number of retained sources per asset (e.g. top 3 by |ρ|) to control dimensionality and limit overfitting.

Important control: include, for every asset j, the sentiment of the other assets at lag 0 as well as the lagged ones. If only significant-lag features are included, the model cannot distinguish "cross-asset sentiment helps" from "the specific lag structure helps" — and a reviewer will ask. Reporting both is what makes the H3 test clean.

Stage 3 — Contagion intensity measurement

Beyond predictive features, quantify the structure of the contagion — this is the finding that goes in the thesis, not just the model:

  • Tier attenuation: does ρ decay with tier distance (T1→T2 > T2→T3 > T1→T3)? Test with an ordered-group comparison.
  • Network structure: build a directed weighted graph where edge weight is ρ_{i→j}(ℓ*). Report in-degree, out-degree and clustering coefficient per tier.
  • Time variation: estimate the contagion strength in rolling windows to see whether it strengthens in high-volatility periods. This links C2 to C3 directly.
  • Directionality: test whether sentiment flows predominantly from large-cap to small-cap, or whether the relationship is bidirectional. Kreuzer et al. (2026) find the BTC→ETH direction; whether that generalises downward is a genuine open question.

On M6 — the reimplementation requirement

Reimplementing HSIF is not optional and not a diversion: it is the control that establishes your improvements are relative to the strongest published multimodal competitor rather than to a weak baseline. Requirements for a defensible reimplementation:

  • Match the published architecture: dual-stream Transformer encoders (3 layers, 4 heads, 64-dim per head), bidirectional cross-attention, global average pooling, concatenation, dense + dropout + sigmoid, weighted BCE, early stopping.
  • Match the published protocol: T = 60-day lookback, min–max scaling per modality, chronological 70/15/15 split, F1-maximising threshold on validation.
  • Use the same feature sets as your other models so the comparison is architectural rather than featuristic. If M6 is evaluated on richer features than M2, any accuracy difference confounds architecture with features.
  • Report the published headline (97.48% accuracy on BTC) only if your reimplementation reproduces it approximately; if it does not, report the divergence as a reproducibility finding rather than hiding it.

TensorFlow/Keras is the natural choice since that is what the original used. Note that the authors used a sentiment embedding matrix (FinBERT probability vectors). Since your sentiment arm is lexicon-based under the free-tier regime, you have two options: (a) use a classifier-free sentiment vector (pos/neu/neg proportions from the lexicon), which is a faithful architectural match with different inputs, or (b) add FinBERT as an optional encoder behind an interface, if you can run a transformer model locally. Choose (a) for the primary comparison and document that the sentiment encoder differs from the original, because that is the honest framing. Option (b) is a stretch task.

4.4.1 Estimation details

  • Target: primary = next-day log return (regression). Secondary = binary direction (classification). Run both; they answer different questions and both are needed for the metrics in §6.5.
  • Optimiser: Adam, learning-rate search {1e-3, 3e-4, 1e-4}, cosine decay or early stopping on validation loss (patience 10, restore best weights).
  • Class imbalance: for the direction task, use compute_sample_weight or class weights; also tune the decision threshold on validation by F1 maximisation rather than defaulting to 0.5. This mirrors the published protocol and materially affects results on imbalanced crypto labels.
  • Regularisation: dropout {0.1, 0.2, 0.3}, L2, early stopping. For tree models: max_depth, min_child_weight, subsample, colsample_bytree, and explicit early stopping on the validation fold.
  • Search budget: a fixed budget per model (e.g. 30 configurations for trees via random search, 20 for deep models) so no model is advantaged by more tuning effort. Document the budget — a comparison where one model got 5 hyperparameter configurations and another got 200 is not a fair comparison and a reviewer will say so.
  • Seeds: run the top 3 configurations with 5 seeds each and report mean ± standard deviation, as both Dashtaki et al. (2025) and Wang (2026) do. A single-run result is not a result.

4.5 Evaluation and statistical protocol (L4)

4.5.1 Walk-forward validation — the primary protocol

  ┌──────────────┐                              ┌──────────────────────────────┐
  │  TRAIN       │▓▓▓ EMBARGO ▓▓▓│    TEST      │      (repeat, rolling)      │
  │  [0 ... t0]  │               │  (t0+61 ... t1]│                              │
  └──────────────┘               └──────────────────┘                           │
  ▲ fitted scaler              ▲ never touched during training                  │
  ▲ feature selection          ▲ SHAP/importance recomputed per fold             │

for each fold k:
    train     = rows[0 : train_end_k]
    embargo   = rows[train_end_k + 1 : train_end_k + 1 + embargo_len]
    test      = rows[train_end_k + 1 + embargo_len : train_end_k + 1 + embargo_len + test_len]
    fit scaler, feature selection and model on train ONLY
    predict on test
    record out-of-sample predictions with a fold manifest

Default configuration: expanding training window, 252-day test folds, 61-row embargo, ~38 folds over a 6-year sample — matching the fold count in Wang (2026) so the results are directly comparable. A purged walk-forward variant (fixed-length training window) should also be run as a robustness check.

4.5.2 Metric implementation notes

  • Compute every metric from the concatenated out-of-sample predictions, not from an average of per-fold metrics. Averaging fold-level R² is meaningless.
  • Report metrics per asset, per tier, per regime and in aggregate. The decomposition is the deliverable.
  • For the direction task, report accuracy, balanced accuracy, precision, recall, F1, MCC, and the AUC-ROC. Report balanced accuracy alongside raw accuracy — with a class imbalance around 52/48 in crypto up/down days, raw accuracy is close to uninformative and a reviewer will notice that a headline accuracy sits near 50–55%.
  • For the return task, report RMSE, MAE, R², and directional accuracy computed from the sign of the predicted return — the economically meaningful metric even for a regression model.
  • Report SMAPE with care: it is undefined for zero values and blows up near zero, which daily crypto returns frequently are. If reported, compute it on price levels or on a sign-safe variant, and say which.

4.5.3 Statistical testing

  • Diebold–Mariano for nested model comparisons on loss differentials (squared or absolute error), with the small-sample Harvey–Leybourne–Newbold correction. Report the DM statistic and p-value per asset and per tier, plus a summary count of how many assets/tiers favour each model.
  • Multiple testing: with ~20 assets × 3 tiers × several comparisons, the family-wise error rate inflates fast. Use the Benjamini–Hochberg procedure at q = 0.05 for the family of tier-level comparisons, and report both raw and adjusted p-values. State this explicitly in the thesis — a paper that runs 60 significance tests and reports the 2 that pass without correction is a paper that will be challenged.
  • Effect sizes with confidence intervals: bootstrap CIs (block bootstrap, 1,000 resamples, respecting serial dependence) on the key effect estimates — the tier elasticity differences and the DM mean differentials.
  • Effectively, this is a panel: consider a panel regression with tier fixed effects and interactions, with asset-clustered or Driscoll–Kraay standard errors (the latter account for cross-sectional correlation, which is exactly what contagion creates). If you find contagion, the residuals will be cross-sectionally correlated, and ignoring that produces over-confident standard errors.

4.6 Backtesting and portfolio layer

4.6.1 Simulation specification

  • Initial capital: 100,000 USD (matching both Dashtaki et al. (2025) and Wang (2026) so results are comparable).
  • Transaction costs: 0.1% per operation (the rate used in the published Algorithm 1 of Dashtaki et al.). Add slippage as a separate scenario: 0 bps, 5 bps, 10 bps, 25 bps. A strategy that only works at zero slippage is not a finding.
  • Position sizing: long/flat and long/short variants, with position sizing as a fraction of equity. Report both, because the long/short variant is where the sentiment signal's asymmetry shows up (Kreuzer et al. find asymmetric positive/negative responses).
  • Benchmark: buy-and-hold of the same asset over the same window, mandatory in every table.

The CER trap — a live error in the current proposal

The proposal lists CER as "Certainty Equivalent Return" with no formula. CER is computable in several different ways, and papers that report "CER" without specifying the formula are not comparable. The same problem appears in Wang (2026), which reports a Sharpe ratio of 1.14 with an annualised return of 78.65% and volatility of 68.94% — but 78.65/68.94 = 1.14, which means their "Sharpe ratio" is computed as return ÷ volatility without annualising the mean return, making it a ratio of annualised quantities rather than the conventional ratio of mean daily excess return to the standard deviation of daily excess return scaled by √365. Do not copy either convention silently. Report the standard definition, state the risk-free rate, and additionally report the ratio-of-annualised-quantities variant so your numbers are comparable with the prior literature you are citing. Reproducing a source's number while fixing its method is defensible; silently copying its method is not.

The causality test, in detail — implement this first

def test_no_future_information(truncated_feature_frame):
    """Recompute every feature at time t using ONLY data up to t.
    If any feature changes, some transform is peeking forward."""
    for t in sample_of_timestamps:
        partial = load_raw_data(up_to=t)
        recomputed = build_features(partial)
        assert_allclose(recomputed.loc[t], features.loc[t], rtol=0, atol=0)

This single test will catch the majority of realistic leakage bugs — centred rolling windows, df.shift(-1), global normalisation, forward-filled sentiment computed from the full series, or a scaler fitted on the whole dataset. It is also the artefact most likely to convince an examiner that the work is rigorous, and it is cheap to implement. Do it before the first model is trained, not after the results look wrong.
