Two pinning rules

1. Pin exact versions in requirements.lock, generated with pip freeze and committed. The requirements.txt may use compatible-release ranges; the lockfile is what the reproduction actually uses. Record the lockfile hash in every run manifest.

2. Expect one genuine dependency conflict and resolve it deliberately, not by uninstalling until it works: scikit-learn, LightGBM and XGBoost each pin different numpy/scipy upper bounds. The usual resolution is a numpy version that satisfies all three — determine it once, pin it explicitly, and note the constraint in the README so the next person does not spend a day rediscovering it.

D. Sentiment glossary construction protocol

The lexicon is a research artefact and must be constructed reproducibly. This protocol makes it one.

  1. Seed corpora. Assemble: (a) the Nakamoto whitepaper (technical terms); (b) 3+ established crypto glossaries; (c) crypto-relevant academic literature including the four papers in this repository; (d) the top 500 terms by frequency in the project's own news corpus.
  2. Candidate generation. Union the seed lists, normalise case and lemmatise, drop duplicates and multi-word expressions that are not domain-specific.
  3. Classification into exactly two lists. CRYPTO_TOPIC_TERMS (topic markers, no polarity — used for density) and CRYPTO_SENTIMENT_TERMS
  4. Polarity assignment. For sentiment terms, assign a polarity in {−1, 0, +1} by two independent reviewers. Disagreements are adjudicated by a third. Record both reviewers' labels so inter-rater agreement can be reported.
  5. Agreement reporting. Report Cohen's κ over the sentiment terms. Expect ≥ 0.7. Below 0.6, rewrite the guidelines and re-label.
  6. Validation. Score the 200-article double-labelled sample (Table 4.1). Report accuracy, precision, recall and F1 against the human labels, per class.
  7. Benchmark. Score the Financial PhraseBank. Report accuracy and F1. The crypto dictionary must not degrade general financial sentiment performance.
  8. Face validity. Inspect the 10 highest and 10 lowest scored articles. Confirm the ranking is sensible.
  9. Freeze and publish. Version the lexicon file, record its hash in every run manifest, and publish it in the thesis appendix so the method is reproducible.
  10. Document the LLM role. If a generative model was used to help generate candidate terms, state it explicitly in the appendix: which model, how it was prompted, and that every candidate was human-reviewed before inclusion. Never present unverified model-generated terms as validated.

Why step 10 is not optional

Kreuzer et al. (2026) used GenAI to derive their crypto dictionary and stated so. Following that precedent is legitimate and citable — but only if the role is disclosed and the human verification is real. A lexicon of unreviewed model-generated terms presented as a research instrument would not survive review, and the "AI-assisted" disclosure would be far more damaging than the method itself. Do the review properly, disclose the assistance, and cite Kreuzer et al. (2026) for the methodology.

E. Team operating checklists

Daily

  • Pipeline run completed; check the freshness panel before doing anything else
  • Open issues triaged at the stand-up; each has an owner
  • Push at least one commit; open a PR rather than committing straight to main

Weekly

  • Friday demo runs the pipeline live in front of the team
  • Retrospective: what slowed us down, what will change
  • Risk register updated
  • Gantt chart updated
  • Every team member can run every workstream's entry point

Before a supervisor review

  • The review pack is drafted (6 pages, §5.4)
  • The exit criterion for the current phase is demonstrably met
  • Any negative finding is written up honestly
  • Blockers list is specific, with the decision needed stated
  • The next fortnight's exit criterion is agreed

Before submission (D64)

  • The §9.3 checklist is complete, item by item, with a name against each
  • make all has been run from a clean clone on a machine other than the developers'
  • Every reported number has been traced to a registry entry
  • The demo has been run end to end by each member
  • The four predictable defence questions have been rehearsed

Final note

This document is a plan, and plans are only useful if they are executed against the gates in Part V. The single most important instruction in it is G2 on day 28: the causality test must pass before any model is trained. Everything else in this project is recoverable — a model underperforms, a hypothesis is refuted, a table comes back null. A result built on leaked data is not recoverable, because it will look good and no one will know to distrust it.

Build the test first. Train second. Report whatever happens.
