IIISystem Architecture

This Part specifies the software system to be built: what it does, how it is decomposed, where each component's data comes from, what it stores, and how it runs. The specification is constrained by three fixed conditions agreed for this project: a free-tier data regime, a research-grade (not production-trading) system, and a multi-tier asset universe spanning popular large-caps and high-risk/new listings.

3.1 Design principles and non-negotiables

PrincipleWhat it means concretely in this build
Reproducibility above allEvery result in the thesis must be regenerable from a clean checkout by one command. No result may exist only in a notebook cell. This is the standard the repository papers set and the one that separates an acceptable capstone from a strong one.
Strict temporal causalityNo computation may ever read data with a timestamp later than the timestamp of the prediction being made. This is enforced in code, not by convention: the feature builder accepts a as_of parameter and every transform filters on it before it aggregates.
Free-tier survivabilityNo component may hard-depend on a paid API. Every source has a documented fallback, and the pipeline must complete end-to-end with zero API keys configured. This is a hard constraint given the 64-day window and a student budget of zero.
Modularity and asset-agnosticismAdding an asset is a configuration change, never a code change. This is what makes the multi-tier panel — the core of contribution C1 — maintainable across the whole project.
Honest evaluationBaselines are tuned with the same effort as the proposed model. Metrics are reported per tier and per regime, never only in aggregate. Negative results are reported with the same prominence as positive ones.
Research-grade, not trading-gradeThe system produces signals and evidence, not orders. There is no exchange connectivity, no order routing, no live capital at risk. This boundary is stated on the dashboard and in the thesis.

Table 3.1 — Design principles. Each one is a constraint that, if violated, produces a specific, named failure later.

3.2 Layered architecture

Why this decomposition and not the proposal's five prose layers

The proposal's §7.5 lists "Data Collection / Processing / Sentiment Analysis / Modelling / Visualization". That is a reasonable conceptual grouping, but as an engineering specification it omits the serving layer, has no storage layer, has no evaluation layer — and it omits the fact that the visualization layer needs an API rather than direct database access. The six-layer split above reflects how the code is actually owned, how it is actually deployed, and where the boundaries that prevent data leakage and result contamination must sit.

3.4 Asset universe and tiering

The user requirement is to cover popular large-caps and high-risk/new listings. The tiering is not cosmetic — it is contribution C1, so the tiers must be defined by a rule applied uniformly and defensibly, not assigned by hand to produce a desired result.

Tier definition

TierRule (applied at the asset's own listing date)PurposeIllustrative members
T1
Large-cap		 Market capitalisation in the top 20 and listed for ≥ 4 years and daily volume above a fixed threshold Deep markets; sentiment should be absorbed efficiently; these are the contagion sources BTC, ETH, BNB, XRP, SOL, ADA, DOGE, LTC
T2
Mid-cap		 Ranked 21–100 by market cap and listed ≥ 2 years Intermediate sensitivity; provides the monotone gradient that H2 tests LINK, AVAX, DOT, MATIC/POL, ATOM, UNI, XLM, ETC
T3
High-risk / new		 Listed < 2 years, or top-100 by market cap but flagged as high-volatility with a documented drawdown history Thin markets where sentiment should have the largest, noisiest effect New 2025–2026 listings, recently-upgraded tokens, small-cap newcomers

Table 3.2 — Tier definitions. Market-cap ranks and listing dates are captured at run time and versioned, so the tier assignment of any asset on any date is reproducible and auditable.

Critical implementation rule for T3

A newly-listed asset has a truncated history. If you evaluate a T3 asset on a fixed 60-day lookback from its listing date, every sample from that asset is warm-up and it contributes nothing. Two consequences follow, and both must be handled in code:

(a) Model training must not require a fixed history length — use a variable-length sequence model with masking, or train per-tier with an asset-appropriate lookback. (b) Assets must enter the evaluation panel only once they have accumulated at least min_history_days of post-listing data (default 90), and the evaluation window per asset must be recorded so that tier comparisons are not confounded with different sample periods.

Without this, T3 results will be systematically weaker for reasons that have nothing to do with sentiment, and H2 will be testing your data pipeline rather than your hypothesis. This is the most likely way the project's central contribution gets invalidated, and it is invisible unless handled deliberately.

On the sentiment source problem — and how it changes the research design

The original proposal assumed X/Twitter and Reddit sentiment. Under the free-tier regime that is not implementable within the schedule. The substitution is not simply "use RSS instead" — it changes what is being measured, and the thesis must reflect that honestly.

What changes: sentiment becomes news-sourced rather than social-sourced. The pipeline therefore measures news sentiment, which is the variable Kreuzer et al. (2026) study — and is arguably better for this project, because Kreuzer show that news sentiment is the rationally-priced channel in institutional futures markets, while social sentiment is the "irrational" component. Since this project targets a tier-stratified, economically-validated study, news sentiment is the more appropriate primary variable.

What this means for the thesis text: replace every occurrence of "social media sentiment" with "news sentiment". Where the free sentiment proxies are used (Google Trends as attention, on-chain/social counts as activity), label them precisely as attention and activity measures, not as sentiment. A reviewer will accept a carefully delimited construct; they will not accept a claim that social sentiment was used when it was not.

What this means for the research value: it actually strengthens the cross-asset framing. Kreuzer et al. show BTC news drives ETH futures — a spillover in the news channel. Testing whether that spillover extends down the tier structure in a news-only setting is a clean, well-delimited question, and it avoids the bot-detection and manipulation problems that a social-media sentiment channel would have required the ethics chapter to address.

Critical: label construction and the embargo

y_ret at time t is defined as log(close[t+1] / close[t]). This means the label at the last row of any split cannot be computed — it depends on the row after the boundary. Therefore:

Every split boundary must be followed by an embargo of at least horizon + lookback rows, and the final rows of the dataset must have their labels dropped entirely. With a 60-day lookback and a 1-day horizon this is a 61-row embargo. Skipping this is the single most common cause of leakage in published crypto papers, and it silently inflates every reported metric. Implement it once, in src/csf/evaluation/splits.py, and never bypass it.

3.7 Configuration and secrets

Configuration is declarative YAML under config/, validated at startup by a typed loader. Secrets are environment variables, never in YAML, never in the repository.

# config/universe.yaml
tiers:
  T1: {min_rank: 1,  max_rank: 20,  min_age_days: 1460, min_quote_vol: 50_000_000}
  T2: {min_rank: 21, max_rank: 100, min_age_days: 730}
  T3: {max_age_days: 730}          # listed < 2y OR flagged high-volatility
assets:
  include:
    - {symbol: BTC/USDT,  role: primary}
    - {symbol: ETH/USDT,  role: primary}
    - {symbol: BNB/USDT,  role: primary}
    - {symbol: SOL/USDT,  role: primary}
    - {symbol: AVAX/USDT, role: primary}
    - {symbol: XRP/USDT,  role: primary}
  exclude:
    - {symbol: USDT/USDT, reason: stablecoin}
    - {symbol: USDC/USDT, reason: stablecoin}
    - {symbol: XMR/USDT,  reason: delisted_may_2024}
min_history_days: 90              # warm-up requirement before an asset enters the panel

Rules

  • Never commit a key. .env is in .gitignore from day one. The pre-commit hook rejects any file containing a string matching (api_key|secret|token)\s*[:=]\s*['"][A-Za-z0-9]{16,}.
  • Every config change is a commit. Config is versioned alongside code so that a result can always be traced to the exact configuration that produced it. The experiment manifest records the config hash.
  • No hard-coded paths. All paths resolve from a single CSF_DATA_ROOT environment variable, defaulting to ./data.
  • Config validation fails fast. Missing asset, unknown tier, negative embargo, or a lookback longer than the shortest asset's history must raise at startup, not midway through a 40-minute training run.

Deployment reality check for a 3-student, 64-day project

The deliverable is source plus a reproducible run plus a local or single-VM deployment — not a public cloud service with SLAs. Any of these satisfies the requirement and is achievable: (a) a documented make all run on a laptop; (b) a Docker Compose stack on a free-tier VM (Oracle Cloud Always Free, Google Cloud e2-micro free tier); (c) a public demo via the api service on a free hosting platform if time permits. Choose one, implement it properly, and document it. Do not attempt a production deployment — the time cost would come directly out of the research, which is what is actually being examined.

Observability and reproducibility

  • Structured logging. JSON logs with run_id, asset, stage, duration_ms. One log line per stage per asset, aggregated at the end of each run.
  • Run manifests. Every pipeline run writes manifest.json: run ID, git commit SHA, config hash, source response hashes, row counts, start/end times, environment lock hash.
  • Failure isolation. One failing source or one failing asset must not abort the run. Each collector returns a status per source; failures are recorded, the run continues, and the dashboard shows a data-freshness panel making gaps visible. Silent partial data is the failure mode this prevents.
  • Freshness SLA. The dashboard displays, per source, the last successful fetch and the expected next fetch. A stale source older than 36 hours is flagged. This is what stops the thesis from reporting results built on a data feed that quietly died in week three.
