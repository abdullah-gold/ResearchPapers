VIIDocumentation & Reporting Standards

The current proposal's documentation is the weakest part of it: prose lists of tools and activities, no artefacts, no standards, and no traceability from a claim to a result. This Part defines the documentation system that will replace it. The governing principle: a claim in the thesis must be traceable to a run; a run must be traceable to a commit, a config, a seed and a data fingerprint.

7.2 Repository policy and Git discipline

Branching

main        ← protected: CI must pass; no direct pushes
  ├─ feat/<issue>-<short>      feature
  ├─ fix/<issue>-<short>       bug fix
  └─ exp/<experiment-id>       experiment branch, merged only if it beats baseline
  • Protected main. Requires CI green + one approving review from a different team member.
  • Short-lived branches. Maximum 3 days. Long branches are where merge conflicts become week-long emergencies.
  • Commit message format: <type>(<scope>): <description> with types feat, fix, data, exp, docs, refactor, test. The exp type is specific to this project: an experiment commit references the run ID it produced.
  • Example: exp(model): XGBoost F4 on T3 assets reaches DA 0.541 (exp_20260514_0031)

What goes in Git and what does not

# Data card: <dataset name>

**Source**          <URL/API endpoint, licence, terms-of-service reference>

**Downstream use**  <which feature sets and models consume it>
**Fingerprint**     <sha256 of the curated parquet; regeneration command>
**Owner / date**    <name>, <YYYY-MM-DD>

Model card template

# Model card: <model_id> v<n>

**Architecture**        <family, layers, hyperparameter search space, selected params>
**Task**                <regression on y_ret / classification on y_dir>
**Training window**     <start – end, folds, embargo, regime composition>
**Feature set**         <F1–F5, exact feature list with version hash>
**Training data**       <assets, dates, sample count per tier>
**Performance**         <metrics per tier and per regime, vs baselines>
**Validation**          <scheme V1–V5, fold count, seeds, mean ± sd>
**Statistical tests**   <DM vs baseline, adjusted p-values>
**Intended use**        <academic research and educational demonstration>
**Out-of-scope uses**   <live trading, investment advice, regulatory decisions>
**Limitations**         <known failure modes, regime sensitivity, data limitations, staleness>
**Ethics**              <no live trading, no order routing, not financial advice>
**Reproduction**        <exact command + expected runtime + seed list>
**Owner / date**        <name>, <YYYY-MM-DD>

The "out-of-scope uses" section is not optional

The model cards must state plainly that the models are research artefacts and are not intended for live trading or investment decisions. This is not just good practice — it is the concrete, enforceable form of the ethics chapter. The proposal promises in §10.1 that the work is "not intended as direct financial or investment advice"; the model card is where that promise becomes an artefact attached to each trained model, which is far stronger than a sentence in a thesis chapter.

ADR template

# ADR-<n>: <title>

**Status**   Proposed | Accepted | Superseded by ADR-<n>
**Date**     YYYY-MM-DD
**Deciders** <names>

## Context
What forced a decision? What constraints applied?

## Decision
What was decided, stated in the active voice.

## Alternatives considered
Each alternative and why it was rejected — this is the part with lasting value.

## Consequences
What becomes easier. What becomes harder. What is now impossible.

ADRs the project will certainly need

  1. Target definition: log returns rather than price levels.
  2. Primary model: tree ensemble rather than LSTM, and why.
  3. Sentiment source: news only, and the exclusion of social media.
  4. Sentiment measure: crypto-density weighting, and the lexicon construction approach.
  5. Primary validation scheme: walk-forward with embargo, over the fixed split.
  6. Tier assignment rule, and the freeze of market-cap snapshots.
  7. Handling of T3 assets with short history: variable-length sequences versus per-tier lookbacks.
  8. Metric definitions, including the exact CER formula and the risk-free rate.
  9. Multiplicity control: Benjamini–Hochberg at q = 0.05.
  10. Scope decisions: what was descoped and why.

7.4 Experiment log and artefact naming

Run ID format

exp_<YYYYMMDD>_<seq>
Example: exp_20260514_0031

Artefact naming

models/registry/<model_id>/<version>/
    artifact.joblib        the trained model
    manifest.json          config, seeds, data fingerprint, metrics
    card.md                the model card
    feature_list.json      exact features with the order used at inference

reports/
    tables/T<no>_<slug>.csv          machine-readable
    tables/T<no>_<slug>.tex          LaTeX for the thesis
    figures/F<no>_<slug>.png         300 dpi
    figures/F<no>_<slug>.svg         vector for the thesis

The dual CSV + LaTeX output is what makes §6.7's rule possible: the thesis's tables are compiled from the LaTeX, which is generated from the CSV, which is generated from the registry. A number cannot be mistyped in the thesis because nobody types it.

Experiment log narrative

Alongside the automatic registry, maintain a human-readable docs/experiment-log.md with a short entry per substantive run:

### exp_20260514_0031 — XGBoost, F4, walk-forward
**Question:** Does lagged cross-asset sentiment add value for T3 assets?
**Setup:**    XGBoost, F4, V2 (38 folds), seeds 42–46, cost 10bps
**Result:**   DA 0.541 ± 0.012 (vs F3 0.528 ± 0.011); DM p = 0.031 (BH adj 0.048)
**Read:**     Supported for T3. No effect for T1 (DM p = 0.62).
**Action:**   Retained in the final model. F4b control added to isolate the lag structure.
**Link:**     models/registry/M2_xgboost/v3/  ·  reports/tables/T6_increments.csv

Entries are short by design. The point is that a reader can reconstruct the project's intellectual history — what was tried, what happened, and why — which is what distinguishes a research project from a code repository.

7.5 Code standards

  • PEP 8 with a 100-character line limit, enforced by ruff. No exceptions without a documented reason in pyproject.toml.
  • Google-style docstrings on every public function: summary, arguments, returns, raises, and — for anything non-obvious — a note on the assumption it relies on.
  • Type hints on public APIs. mypy clean for features/, evaluation/, modelling/.
  • No bare except. Catch specific exceptions. The ingestion layer catches specific HTTP errors; the model layer lets training errors propagate.
  • No magic numbers. Every window length, threshold, lag and rate limit lives in config/*.yaml with a comment. This is what makes the sensitivity analysis possible.
  • Deterministic by default. Every module that consumes randomness takes a seed argument. No global np.random.seed inside a library function.
  • Fail loudly in the research path, softly in the serving path. A training run must crash on bad data. A dashboard request must degrade gracefully. Mixing these two behaviours is a common source of silently wrong results.
  • Comments explain why, not what. # shift by one day so the feature uses only past information is useful. # increment i is not.

7.6 Figure and table standards

Figure rules

  • Numbering: "Figure 3.1 —" by chapter, caption below the figure, descriptive and self-contained (a reader should understand it without the surrounding paragraph).
  • Resolution: 300 dpi for raster, SVG for anything that will be scaled or edited. Never paste a matplotlib default 100 dpi screenshot into a thesis.
  • Legibility: axis labels at ≥ 9 pt at final printed size; a legend outside the data area; no chart junk; no 3-D anything.
  • Colour: a colourblind-safe palette, used consistently across every figure in the thesis. Semantic mapping: sentiment = one hue, price = another, model A/B/C = a fixed set of three. Fix the palette once and never change it. Also encode the key distinction with line style or marker shape, so the figures survive greyscale printing.
  • Source attribution: any figure reproducing or adapting a published figure says so. Adapted figures require permission where the licence requires it. Both Dashtaki et al. (2025) and Kreuzer et al. (2026) are open access under CC-BY, which permits adaptation with attribution — verify the specific licence and the specific figure, and record the permission in the acknowledgements if the journal requires it.

Table rules

  • Numbering: "Table 5.2 —", caption above the table.
  • Every table states its sample: n, the assets, the period, and the validation scheme, in the caption. A table without a sample description is unusable.
  • Bold the best result per column, and italicise the second best. State the convention once in the first table's caption.
  • Report mean ± sd across seeds for anything stochastic. Single numbers are for deterministic quantities only.
  • Significance markers: *, **, *** for p < 0.05, 0.01, 0.001; state the correction applied in the caption.
  • No more than 7 columns in a table meant to be read in a document. Wider tables belong in an appendix.
  • All tables are generated. Never type a number into a thesis table by hand.

7.7 Report writing standards

RuleSpecification
Every number is traceableEach figure and table cites its generating run ID in the caption or a footnote. The reproducibility appendix maps every headline number to its run.
Results before interpretationState what happened, then what it means. Never interpret before the data is on the page. An examiner should be able to read the results section and disagree with your interpretation without you having pre-empted them.
Report the negative resultsWhich models failed, which feature sets added nothing, which hypotheses failed. A thesis with only positive results is less credible, not more.
No causal language without a causal designUse "is associated with", "predicts", "leads" — never "causes" — unless the design supports causation. The Granger test is predictive precedence, not causation.
Define on first useEvery metric, acronym and technical term is defined at first use. Rebuild the acronym table from scratch (Appendix F) and place it correctly.
Compare against prior work explicitlyWhere a number is comparable to a published figure (accuracy vs Dashtaki et al., Sharpe vs Wang, sentiment coefficients vs Kreuzer et al.), say so and state the differences in setup. Where it is not comparable, say that too.
Limitations are specificNot "the sample is small" but "T3 assets contribute 640 usable observations against 2,900 for T1, so the tier comparison for T3 is underpowered at the 5% level". Specific limitations are credible; generic ones are filler.
One voice, past tense for work, present for findings"The pipeline collects…" for the system; "Sentiment is associated with…" for the findings. Consistent tense throughout.
Passive constructions avoidedPrefer active. "The model was trained on…" → "We trained the model on…".
No claim without a citationEvery factual assertion about prior work, every market-structure claim, every method description carries a citation. Every citation appears in the reference list; every reference list entry is cited.
